# Stiger Wire-Format Specification

<!-- public-mirror-banner -->

> **Public mirror.** This repository is automatically synchronised from the
> `spec/` directory of the (private) Stiger source tree. Filing issues against
> the spec here is fine; canonical edits happen upstream and propagate on
> every push to Stiger's `main`.

This directory is the **normative specification** of the data formats [Stiger](https://onegoodman.studio/stiger)
embeds inside PNG sticker images. It exists so that anyone — paranoid user,
auditor, journalist with a captured sticker — can:

1. Read the spec and understand bit-for-bit what is on the wire.
2. Run a reference decoder (`reference/python/`, `reference/typescript/`) on a real sticker.
3. Compare the result against vectors that were generated by the shipping
   Swift engine (`test-vectors/`).

If the binary on your phone does anything different from what is described
here, that is a bug. File an issue.

## Layout

| File | What it covers |
|------|----------------|
| [`lsb-layer.md`](lsb-layer.md) | From PNG pixels to a short byte stream: eligible pixels, the permuted walk, the syndrome-trellis code. Shared by both modes. |
| [`open-v2.md`](open-v2.md) | Open mode framing — public, no privacy. |
| [`stealth-v4.md`](stealth-v4.md) | Stealth mode framing + cryptography. The mode that protects messages. |
| [`open-v1.md`](open-v1.md), [`stealth-v3.md`](stealth-v3.md) | **Superseded.** The formats of the TestFlight beta, kept as history; no shipping decoder reads them. |
| [`reference/python/`](reference/python/) | Reference decoder and a reference encoder, no Stiger code involved. |
| [`reference/typescript/`](reference/typescript/) | Reference decoder for browsers and Node; the one the site's demo runs. |
| [`test-vectors/`](test-vectors/) | Known PNGs + passwords + expected plaintext, emitted by the Swift engine. |

## Stability

Versioned by mode. `open-v2` and `stealth-v4` are the current formats; an
incompatible change requires a new version number and a new spec file, and
the reference decoders handle every version that reached a released build.

`open-v1` and `stealth-v3` never reached a release: they were the formats of
the public TestFlight beta, and the owner retired them on
2026-11-08 without a compatibility period — there was no installed base
worth carrying them for. Their documents stay here as history; the shipping
decoders and the reference decoders do not read them (git keeps the old
reference code). A sticker made by a beta build does not open in a release
build.

The encoder side is *not* part of this spec: an attacker who can choose what
to embed already has the password, so encoder behaviour is implementation
detail. Only the decode path is normative. `lsb-layer.md` §7 describes the
engine's encoder anyway, as a SHOULD, because the detectability of a carrier
depends on it.

## A note on transport

How a Stiger PNG reaches the recipient is a separate concern from the wire
format and is **out of scope here**. The reference decoder accepts PNG bytes
from any source. For the shipping iOS app's actual transport (image
attachment via `MSConversation.insertAttachment`, deliberately not
`MSSticker`) and the empirical findings behind that choice, see
[`../README.md`](../README.md) → "Carrier transport".

## A note on `tEXt` chunks in beta stickers

Stickers produced by the Swift engine **in the TestFlight beta (builds through
48)** contain a `tEXt` chunk with the keyword `Comment` and a payload of random
printable ASCII bytes, inserted before `IEND`. It was a transport-layer
size-normalization wrapper (see [`THREAT_MODEL.md`](THREAT_MODEL.md)
§8, "History") that padded every outgoing PNG to a per-image target size.
Build 49 onward does not write it. Files from the beta are still in
circulation (the beta was shown at Ekoparty 22 on 2026-10-09), so a PNG
parser may still meet the chunk; it is not part of any wire format defined
here and every standard PNG library drops it before exposing pixels.

## Threat model

This spec defines a **wire format**, not a threat model. For the security
goals these formats are meant to achieve and the assumptions behind them,
see [`THREAT_MODEL.md`](THREAT_MODEL.md).
